# CoreFlow MTP 系统设计

## 分层

1. `profiler/` 与 `predictor/` 描述执行成本；`allocator/` 结合请求流、复用和显存约束生成 context 分区与 GPU 分配。
2. controller 推进完整 DAG，父子输入绑定本次真实输出，不发送预设输出强制生成。
3. scheduler 根据完整 prompt 真实 token 长度、实际缓存与负载选择实例。
4. `runtime/` 使用 vLLM 0.18.1 V1；K 在实例初始化时固定。
5. 项目自有 scheduler／worker 扩展负责真实缓存引用、CPU 换出、恢复与同机迁移，不修改安装环境中的 vLLM 文件。

## K 与 context

K=0 不创建 speculative configuration；K>0 使用原生 `method=mtp`。正式推理不人工展开 Q/K/V，不使用 dummy 权重或指定输出回放。

路由 context 是当前提交的完整 prompt token 数，包含已有用户、agent、工具和生成历史。分区为 `[lower, upper)`，模型最大长度另行约束。生成中途越过区间不会迁移运行中的请求；可在完成后迁移可复用前缀。

## 资源规划

原两层算法保留：先为各 agent 建立 GPU预算—吞吐映射，再按 workflow 瓶颈分配 GPU。容量表可携带区间的 K；其来源、模型与执行配置必须明确。

K=0 的新环境组件模型当前只支持 Llama、TP=1、FA2。Qwen3.5 是 hybrid，MTP 有自己的成本、有效产出和临时状态，不能复用 Llama AR 系数或直接对旧吞吐乘固定加速比。

不同分区选择不同 K 时，缓存转换与重算成本必须进入容量评估；当前跨实例缓存协议明确拒绝跨 K 转换，不能把各区间独立选出的最优 K 当成无额外成本。

## 执行与观测

chunked prefill、APC、eager／graph、调度预算均属于容量标定配置。纯 decode 的局部速率不是完整服务容量，更不是 workflow 完成率。实验中的同步 trace 属于诊断，正式性能测量应关闭。

固定历史请求可用于受控 profiling；端到端验证仍需完整 workflow 依赖、真实父子输出与明确的工具行为。外部 agent／工具框架不由本项目自动重建。
